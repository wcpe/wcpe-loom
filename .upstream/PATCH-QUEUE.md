# WCPE Loom 补丁队列规范

本规范定义 WCPE Loom 相对上游基底的补丁如何组织、标注与校验。流程借鉴 Debian quilt / DEP-3 实践。

## 1. 队列结构

历史自基底起分为三段，边界由 tag 标记：

```
base/essential-1.15-713489a9      ← 基底快照（不可变）
  ↓  补丁队列：每个提交 = 一个补丁 = 一个逻辑变更单元
patch-queue/v1.15-wcpe.N          ← 队列末端标记
  ↓  仓库元数据：非补丁内容，按普通提交维护
HEAD
```

- **基底**：上游的一个不可变提交快照，用 `base/<来源>-<代系>-<sha 前 8 位>` 注释 tag 固定。基线一旦固定不再移动；换基底等于换 tag。
- **补丁队列**：基底之上的线性提交，**禁止 merge 提交**。队列可被线性重放到新基底。
- **仓库元数据**：CI、文档、发布脚本、队列自身的清单。这些内容属于本仓库而非补丁（类比 Debian 源码包中的 `debian/` 目录），不参与补丁队列。

## 2. 补丁的判定标准

一个补丁是一个**逻辑变更单元**，须同时满足：

1. 能用一句话说明其目的；
2. 能独立审查，不必先读队列中其他补丁；
3. 撤销它不牵连其他补丁的功能。

据此有三条操作规则：

| 情形 | 处置 |
|---|---|
| 上游一个提交恰好是一个逻辑变更 | 1:1 保留，原样入队 |
| N 个提交共同构成一个逻辑变更（开发中的多次迭代） | **压缩为一个补丁** |
| 一个提交混合多个不相关的变更 | **拆分为多个补丁** |

**压缩判据**：若补丁 B 修改的内容全部是补丁 A 新增或修改过的行，B 必须压缩进 A。补丁队列描述的是**最终状态**，不是开发过程的年表；"先实现、再修正实现"的中间态不属于队列。

## 3. 溯源标注

每个补丁的提交信息末尾附溯源块，字段取自 Debian DEP-3：

```
<type>(<scope>): <中文描述>

<正文：说明为什么改、改动要点>

Origin: vendor, wcpe-loom
Forwarded: not-needed
```

| 字段 | 取值 | 含义 |
|---|---|---|
| `Origin` | `upstream, <提交URL>` | 取自上游，可原样保留 |
| | `backport, <上游版本>` | 从其他代系向后移植 |
| | `vendor, wcpe-loom` | 本项目自研，永不上游 |
| `Forwarded` | `no` | 应当反馈上游，尚未反馈 |
| | `not-needed` | 本项目专属，无需反馈 |
| | `<URL>` | 已反馈，附链接 |
| `Applied-Upstream` | `<版本或提交>` | 可选。上游已收录 → 换基底时**直接删除该补丁** |

`Applied-Upstream` 是队列不无限增长的机制：上游采纳后补丁即被移除。

## 4. 不入队列的内容

下列内容属于仓库元数据，**不得**混入补丁提交：

- `.github/workflows/` — CI 工作流
- `README.md`、`CHANGELOG.md` — 项目文档
- `scripts/`、`PATCH-QUEUE.md`、`.upstream/` — 维护工具与队列清单
- `build.gradle` 中的发布段（`publishing`、版本导出）

判断方法：改动若在"把本仓库当作一个独立项目"时仍然成立（与上游代码无关），它就是元数据。

## 5. 校验

```bash
scripts/sync-upstream.sh verify
```

检查项：

1. 基底 tag 存在，且是 HEAD 的祖先；
2. 基底到队列末端之间无 merge 提交；
3. 队列末端到 HEAD 之间只含元数据改动（不触碰 `src/main/java`）；
4. 队列中每个提交都带 `Origin` 与 `Forwarded` 字段；
5. 队列提交信息的 type 属于 `feat`/`fix`/`refactor`/`perf`/`test`/`build`/`docs`/`chore`/`ci`。

## 6. 换基底流程

```bash
scripts/sync-upstream.sh essential-rebase
```

在候选分支上把补丁队列重放到新基底，随后逐项人工核对：

1. `git cherry` 预览哪些补丁已被新基底收录 → 对应补丁删除；
2. `git range-diff` 对比重放前后队列差异；
3. 构建验证；
4. 通过后更新基底 tag 与 `.upstream/essential-base`。
