# 发布点 → 主线提交对照表
#
# 为什么需要这张表：本仓库为整理补丁队列会重写历史，已经打过 tag 的发布点可能被留在主线
# （dev/1.17-wcpe）之外。此时直接拿两个 tag 做 `A..B` 区间，git 与 GitHub 的 compare 都会
# 退到共同祖先重算，把上一版已发布的提交重复算进下一版。实测 1.17.12→1.17.13 因此多出
# 4 个提交、GitHub 显示 status: diverged。
#
# 为什么不能自动推断：重写同时改变了内容与时间戳——
#   - 按内容（tree）匹配：1.17.12 与主线上最近的候选相差 6 个文件（主线在它之后又吸收了别的内容），
#     找不到 tree 相同的提交；
#   - 按标题匹配：同名提交在主线上可能有多条，实测会误命中共它版本的提交；
#   - 按时间匹配：重写把提交时间改成了重写时刻（实测 0001f7c4 的 %cI 是 21:28，而 tag 的
#     taggerdate 是 11:05），时间轴同样失真。
# 因此这张表由人工维护：发版时把「上一版 tag」对应的主线提交记下来。
#
# 格式：<tag> <主线提交 SHA 或 ref>，每行一条，# 开头为注释。
# 未列出的 tag 按原样使用（若它在主线历史内则无需列出）。

# 1.17 线：孤立 tag 与其主线等价提交
# 1.17.10 / 1.17.11 本身在主线历史内，不必列出。
#
# 锚点判据（务实版）：锚点要保证「发布之后才加的补丁不被当成已发布」。
# 重写会改变补丁段与元数据段的相对位置，因此**没有任何单点锚点能精确切出「该版本发布的内容」**，
# 只能在「漏列」与「重列」之间取舍——本表统一选择**宁可重列、不可漏列**：
#   - 漏列会让用户以为某个修复不存在（实际已发布），危害更大；
#   - 重列只是多几条说明文字，不影响任何代码或产物。
#
# 1.17.13 的三种候选与实测结果（供以后遇到同类问题时参考）：
#   - b9ed0d90（加入 jar-processor-hash 之后）：把该补丁当成已发布 → 1.17.14 **漏列**它。已弃用。
#   - 3306b08d（元数据重放后的同位置）：它排在补丁段之后，漏掉 2 个新补丁 → 同样**漏列**。
#   - 6f58ad25（1.17.13 发布时的补丁段末端）：**重列** 1.17.13 自己的 5 个元数据提交，
#     但 2 个新补丁一个不漏。选用这个。
#
# 1.17.1 / 1.17.2 / 1.17.3：都是主线之外的早期发布点，但**彼此之间可直接比较**，
# 不需要换到主线——按 jar 内容核对过：
#   - 1.17.1 与 1.17.2 的共同祖先就是基底 026ce830（1.17.1 是旁支），区间即 1.17.2 的全量变更；
#   - 1.17.2 → 1.17.3 共同祖先是 7b7ccbd2，属正常递进。
